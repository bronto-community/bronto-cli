Everything you can configure in Bronto has a resource command, and they all work the same
way. Learn the pattern once and it applies to datasets, monitors, API keys, and the rest.

<Tape name="resources" title="Listing, inspecting, and changing resources" />

## The pattern

```sh
bronto <resource> list
bronto <resource> get <id-or-name>
bronto <resource> create -f key=value -f other=value
bronto <resource> update <id-or-name> -f key=value
bronto <resource> delete <id-or-name> --yes
```

For example:

At a terminal, `list` prints a table of the most useful columns and `get` prints the whole
object as JSON.

Exceptions: no `get` for `parsers`, `api-keys`, `forward-configs`, `webhooks`, `slack`, `monitors downtimes`; no `update` for `metrics`, `exports`.
`collections`, `log-views`, and `permissions` are list-only, and `metrics` is read-only
(`list` and `get`, plus `top-keys`). The generated
[command reference](/reference/commands/) lists the exact verbs for each resource.

## Names work wherever ids do

Every command that takes an id also takes a unique name:

- Datasets resolve by name, or by `collection/name` when the name exists in more than one
  collection.
- Users resolve by email.
- Roles resolve by id or `display_name`. System roles have readable ids such as `Admin`
  and `ReadOnly`.
- Monitors, dashboards, and the rest resolve by `name`. Quote names with spaces.

If a name matches more than one resource, the command fails with exit code 2 and lists the
candidate ids so you can pick one.

## Creating and updating

`create` and `update` build the request body from repeated `-f key=value` flags. Each
value is parsed as JSON when it can be, so numbers, booleans, arrays, and objects keep
their type, and anything else is sent as a string:

```sh
bronto dashboards create -f name=Overview -f description=Prod
bronto parsers update <id> -f name=nginx-combined
bronto groups create -f name=sre
```

For larger bodies, pass a JSON file with `--input`, or `--input -` to read stdin. `-f` and
`--input` can't be combined.

```sh
bronto monitors create --input monitor.json
./generate-monitor.sh | bronto monitors create --input -
```

The body is sent as is, so the fields are whatever the
[Bronto API](https://docs.bronto.io/api-reference/introduction) expects for that
resource. Updates to `monitors`, `widgets`, `datasets`, and `roles` use HTTP PUT. For
widgets and roles that replaces the whole object, so send every field you want to keep.

## Deleting

`delete` asks for confirmation at a terminal. In a script there's no one to ask, so it
refuses with `usage_confirmation_required` (exit code 2) unless you pass `--yes`:

```sh
bronto api-keys delete <id> --yes
```

## Preview changes with --dry-run

`--dry-run` works on every command that changes something. Reads still run, so names are
resolved and a name that doesn't exist fails as it would for real. Nothing is changed.

`create` and `update` print the request they would send as a JSON plan on stdout: method,
path, and body. `delete` and some action verbs, such as `groups add-members`,
`monitors mute`, and `users deactivate`, print a one-line `DRY RUN:` note on stderr
instead. `delete` also skips its confirmation prompt, because nothing is deleted.

```console test tty
$ bronto dashboards create -f name=Overview -f description=Prod --dry-run
{
  "body": {
    "description": "Prod",
    "name": "Overview"
  },
  "dry_run": true,
  "method": "POST",
  "path": "/dashboards"
}
$ bronto monitors delete "Payments latency p95" --dry-run 2>&1
DRY RUN: would delete monitor Payments latency p95.
```

## Commands beyond CRUD

A few resources have extra verbs:

| Command | What it does | Guide |
| --- | --- | --- |
| `bronto monitors events`, `bronto monitors notifications` | recent events and sent notifications | [Monitors](/guides/monitors-and-dashboards/#monitors) |
| `bronto monitors mute`, `bronto monitors check` | mute a monitor, lint definitions in CI | [Monitors](/guides/monitors-and-dashboards/#monitors) |
| `bronto dashboards attach-widgets`, `bronto dashboards remove-widget`, `bronto dashboards detach-from-template` | assemble dashboards | [Dashboards](/guides/monitors-and-dashboards/#dashboards-and-widgets) |
| `bronto widgets attach-widgets`, `bronto widgets remove-widget` | nest widgets | [Dashboards](/guides/monitors-and-dashboards/#dashboards-and-widgets) |
| `bronto groups members`, `bronto groups add-members`, `bronto groups remove-members` | group membership | [Access management](/guides/access-management/) |
| `bronto users groups`, `bronto users deactivate`, `bronto users reactivate`, `bronto users resend-invite` | user lifecycle | [Access management](/guides/access-management/) |
| `bronto datasets parser get`, `bronto datasets parser set`, `bronto datasets parser unset` | assign a parser to a dataset | below |
| `bronto metrics top-keys` | attribute keys seen on a metric | below |

### Assign a parser to a dataset

`bronto datasets parser` shows or changes which [parser](https://docs.bronto.io/core-features/custom-parser)
a dataset uses:

```console test tty
$ bronto datasets parser get prod/checkout-service
{
  "parser_id": "8d0f2b4c-6e7a-4c9d-9f3b-4c6e8a0d2f16",
  "parser_name": "json"
}
```

```sh
bronto datasets parser set prod/checkout-service <parser>
bronto datasets parser unset prod/checkout-service
```

### Metric attribute keys

`bronto metrics top-keys <metric>` lists the attribute keys seen on a metric, the
metrics counterpart of `bronto fields`:

```sh
bronto metrics top-keys system.cpu.utilization --since 1h
```

## API keys

`bronto api-keys list` masks key values in every output format, JSON included, so keys
don't end up in CI logs by accident. Pass `--reveal` to see them in full.

```console test tty
$ bronto api-keys list
NAME     API_KEY    CREATED     ID
docs-ci  bronto_d…  2026-05-04  7c9e1a3b-5d6f-4b8c-8e2a-3b5d7f9c1e15
```

## Usage

`bronto usage` shows ingestion, search, and export volume over a period (default `7d`):

```console test tty
$ bronto usage --since 7d
TIME              EVENTS  VOLUME
2026-07-19 09:00  41      9.5 kB
2026-07-19 09:05  39      9.1 kB
2026-07-19 09:10  40      9.3 kB
2026-07-19 09:15  38      8.9 kB
2026-07-19 09:20  52      13.6 kB
2026-07-19 09:25  34      7.9 kB
```

For per-dataset numbers, call the API directly with
`bronto api GET /usage/organizations/logs` (see [the api command](/extend/api/)).

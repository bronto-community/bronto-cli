bronto can trace its own runs with OpenTelemetry. This is off by default, and nothing is
sent anywhere unless you configure an exporter with the standard `OTEL_*` environment
variables. bronto has no telemetry flags or config keys of its own.

## Turn it on

Point bronto at an OTLP endpoint:

```sh
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
bronto search 'status >= 500' -d prod/checkout-service --since 1h
```

Each run produces:

- A root span named after the command, such as `bronto search` or `bronto monitors list`.
  It records `process.exit.code`, and on failure `error.type`, which holds the
  [error code](/reference/exit-codes/) (for example `auth_invalid_key`).
- A client span for each HTTP request to the Bronto API, retries included, as children of the
  root span.

Spans are flushed when the command exits. If the backend can't be reached, the exit is
delayed by at most 3 seconds, and the command's exit code and output don't change.

To send bronto's traces to Bronto itself, use your region's ingestion endpoint and an
ingestion API key. See [Send Traces to Bronto](https://docs.bronto.io/tracing/send-traces):

```sh
export OTEL_EXPORTER_OTLP_ENDPOINT=https://ingestion.eu.bronto.io
export OTEL_EXPORTER_OTLP_HEADERS="x-bronto-api-key=$BRONTO_INGEST_KEY"
```

## Continue a trace

When `TRACEPARENT` is set, bronto's root span becomes a child of that trace. `TRACESTATE` and
`BAGGAGE` are read too. This is the
[environment-variable carrier](https://opentelemetry.io/docs/specs/otel/context/env-carriers/)
convention that CI integrations and tools like
[otel-cli](https://github.com/equinix-labs/otel-cli) use, so a bronto call inside a traced
pipeline step shows up inside that step's trace:

```sh
# Inside a step whose tracer exported TRACEPARENT
bronto send -d deploys -m "deployed $GIT_SHA"
```

The trace context is passed on even when export is off. With `TRACEPARENT` set, requests
to the Bronto API carry a W3C `traceparent` header, and
[exec plugins](/extend/plugins/) get `TRACEPARENT`, `TRACESTATE` and `BAGGAGE` in their
environment. When bronto is exporting, those values point at bronto's own spans, so a
plugin's spans nest under the bronto command that ran it.

## Settings

bronto reads these:

| Variable | Effect |
| --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | Setting either one turns on OTLP export. |
| `OTEL_TRACES_EXPORTER` | Comma-separated list of `otlp`, `console` or `none`. `console` writes spans to stderr (not stdout, which carries the command's output). `none` turns export off. When this is unset, `otlp` is used if an endpoint is set. |
| `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` | `http/protobuf` (default) or `grpc`. |
| `OTEL_SDK_DISABLED` | `true` turns tracing off, whatever else is set. |
| `OTEL_SERVICE_NAME` | Overrides `service.name`, which defaults to `bronto-cli`. |
| `OTEL_RESOURCE_ATTRIBUTES` | Extra resource attributes, such as `deployment.environment.name=ci`. |
| `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG` | Sampler. The default, `parentbased_always_on`, follows the sampled flag in `TRACEPARENT`. |
| `OTEL_LOG_LEVEL` | Export and configuration errors are silent by default, so they don't mix into stderr output that scripts parse. Set this to any value other than `none` to print them. |
| `TRACEPARENT`, `TRACESTATE`, `BAGGAGE` | The trace context to continue. |

The OTLP exporters also honor the rest of the standard exporter settings, such as
`OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_EXPORTER_OTLP_TIMEOUT`, `OTEL_EXPORTER_OTLP_COMPRESSION`
and `OTEL_EXPORTER_OTLP_CERTIFICATE`, plus their `_TRACES_` variants.

## What's recorded

Spans carry the command path and HTTP request details, including the request URL, but no
command arguments, flag values, or API keys. Only traces are exported. bronto doesn't emit
OpenTelemetry metrics or logs.

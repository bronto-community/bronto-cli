title: CI/CD
description: Run the bronto CLI in CI pipelines and containers with environment-only credentials, the published Docker images, and no keychain.
---

In CI there's no one to type a key and usually no OS keychain. Pass the credentials
through the environment and the CLI won't touch the keychain.

## Credentials from the environment

```sh
export BRONTO_API_KEY=<management-key>   # from your CI secret store
export BRONTO_REGION=eu                  # or us
bronto ping
```

Once `BRONTO_API_KEY` is set, no keychain lookup happens. `BRONTO_REGION` defaults to
`eu`, so set it if your account is in `us`. Use the least-privileged key that works: an
ingestion-only key for jobs that only run `bronto send`, a Search key for read-only jobs.
[API Keys](https://docs.bronto.io/Account-Management/API-Keys) lists the roles.

To fail a pipeline early on a bad credential, run `bronto auth status`. It exits non-zero
if the API rejects the key:

```sh
bronto auth status
```

## GitHub Actions

The [Setup bronto CLI](https://github.com/marketplace/actions/setup-bronto-cli) action installs
the bronto CLI on Linux, macOS, and Windows runners (amd64 and arm64) and puts it on `PATH`:

```yaml
jobs:
  check-monitors:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: bronto-community/setup-bronto-cli@v1
        with:
          version: 0.8.1
          api-key: ${{ secrets.BRONTO_API_KEY }}
          region: eu
      - name: Lint monitor definitions
        run: bronto monitors check --input monitors/checkout-5xx.json --input monitors/payments-p95.json
```

- `version` pins the bronto CLI, so a new release doesn't change your pipeline unannounced. Leave
  it out to get the latest release.
- `api-key` and `region` are exported as `BRONTO_API_KEY` and `BRONTO_REGION` for the later
  steps, and the key is masked in logs. You can also set those variables yourself with `env:`.
- Every download is checked against the release's `checksums.txt`, and the action verifies the
  cosign signature on that file, as described in [Install](/cli/getting-started/install#verify-a-release).

On other CI systems, or without the action, use the install script:

```sh
curl -fsSL https://raw.githubusercontent.com/bronto-community/bronto-cli/main/scripts/install.sh | VERSION=v0.8.1 BINDIR="$HOME/.local/bin" sh
```

## Docker

The published images contain only the binary (plus CA certificates), with `/bronto` as
the entrypoint:

```sh
docker run --rm -e BRONTO_API_KEY -e BRONTO_REGION \
  ghcr.io/bronto-community/bronto-cli:latest monitors list -o json
```

There's no shell, package manager, or keychain daemon in the image, by design. Pass
credentials as environment variables, not files. For a base with a little more in it,
use the `-distroless` tag. [Install](/cli/getting-started/install) lists
the available tags.

To feed a file into a command, mount it and use `--input`, or pipe it to stdin with
`docker run -i`:

```sh
docker run --rm -i -e BRONTO_API_KEY -e BRONTO_REGION \
  ghcr.io/bronto-community/bronto-cli:latest monitors check --input - < monitors/checkout-5xx.json
```

## Restricted environments

Sandboxes and locked-down runners often have no keychain and a read-only home directory.

- Set `BRONTO_API_KEY` and `BRONTO_REGION`. That's all most commands need.
- If you need `bronto config set` or profile files, point `BRONTO_CONFIG_DIR` at a
  writable directory. The CLI reads and writes `bronto/config.toml` under it, and the
  fallback `bronto/credentials` file if there's no keychain.
- Don't commit an API key to `.bronto.toml`. The CLI refuses to read `api_key` from any
  config file.

## Tips for CI

- Make destructive steps explicit with `--yes`. Without it, `delete` refuses to run
  outside a terminal.
- Run mutating steps with `--dry-run` in pull-request jobs and for real on the main branch.
- Branch on [exit codes](/cli/reference/exit-codes). `5` means rate limited or timed out.
  Retrying is safe for reads; a timed-out write may already have landed, so check before
  you retry it.
- Add `--quiet` to keep logs to data and errors, and `--debug` when a step fails and you
  need to see the requests.
- `bronto api-keys list` masks key values even in JSON, so it's safe to print in logs.

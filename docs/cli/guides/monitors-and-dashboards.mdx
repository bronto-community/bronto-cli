page covers their extra commands.

## Monitors

alerts when a condition holds. The [monitors API reference](https://docs.bronto.io/api-reference/monitors/retrieve-monitors)
lists every field a monitor takes. To see what a monitor has been doing:

### Mute and unmute

```sh
bronto monitors mute "High 5xx rate on checkout"                       # until you unmute it
bronto monitors mute "High 5xx rate on checkout" --until <epoch-ms>    # until a future time, in epoch milliseconds
bronto monitors mute "High 5xx rate on checkout" --unmute
```

`--until -1`, the default, mutes indefinitely. Any other `--until` must be a future time
in epoch milliseconds, and `--unmute` can't be combined with `--until`: the command
refuses either mistake with exit code 2. With `--dry-run` it prints the request it would
send, with the monitor's name resolved to its id:

{/* test: tty */}
```console
$ bronto monitors mute "High 5xx rate on checkout" --dry-run
{
  "body": {
    "mute_until": -1
  },
  "dry_run": true,
  "method": "POST",
  "path": "/monitors/a1f3c9d2-4b6e-4f81-9c2d-7e5b3a8f1c01/status"
}
```

### Downtimes and templates

Downtimes schedule planned quiet periods. They support `list`, `create`, `update`, and
`delete`, and resolve by id or name. A downtime needs a `name`, a `description`, the
monitor ids it silences in `from`, and either a `static_time_range` (epoch milliseconds)
or a recurring `dynamic_time_range`:

```sh
bronto monitors downtimes list
bronto monitors downtimes create -f name=deploy -f description="Friday deploy" \
  -f 'from=["<monitor-id>"]' -f 'static_time_range={"from":<start-ms>,"to":<end-ms>}'
bronto monitors downtimes create --input downtime.json
```

`bronto monitors downtimes update` replaces the whole downtime, so pass all of these
fields again.

Monitor templates have the full set of verbs under `bronto monitors templates`. In a
template `create` body, `threshold` is a string (`-f 'threshold="1000"'`); see
`bronto monitors templates create --help` for the other required fields.

Monitor updates replace the whole monitor too: `bronto monitors update` needs the full
body, so keep it in a file and pass it with `--input`.

### Lint monitor definitions in CI

If you keep monitor definitions as JSON in a repository, `bronto monitors check`
validates them before you apply them. It checks query syntax, window bounds, and that the
referenced datasets exist. On any problem it exits 1 with `monitor_check_failed`:

```sh
bronto monitors check --input monitors/checkout-5xx.json --input monitors/payments-p95.json
```

`--input` is repeatable and takes `-` for stdin. Run `monitors check` in CI before
`bronto monitors create --input <file>` so a broken definition fails the build instead of
being created.

## Declarative dashboards

Describe a dashboard in a YAML file and `bronto dashboards apply` builds it: the metric
definitions, the widgets that plot them, and the dashboard, with no ids to copy between
commands. Run it again after editing the file and it changes only what you changed, like
`kubectl apply`. This is the way to build a dashboard; the commands in the next sections
are the pieces it uses.

A dashboard for a service's traces, with a request rate, a p95 latency in milliseconds,
and an error rate:

```yaml checkout.yaml
name: Checkout API health
description: Request rate, latency and errors for checkout-service
tags: {team: checkout}
widgets:
  - name: Request rate
    type: line
    queries:
      - name: requests
        dataset: .traces/checkout-service
        select: count(*)
        where: $span.kind = 'SPAN_KIND_SERVER'
  - name: p95 latency
    type: line
    unit: nanoseconds          # $span.duration_nano is in ns; the web UI shows "640 ms"
    queries:
      - name: p95
        dataset: .traces/checkout-service
        select: $span.duration_nano
        agg: p95
        where: $span.kind = 'SPAN_KIND_SERVER'
        group_by: [$span.name]  # one line per operation
  - name: Error rate %
    type: line
    queries:
      - name: errors
        dataset: .traces/checkout-service
        select: count(*)
        where: $span.status_code = 'STATUS_CODE_ERROR'
      - name: total
        dataset: .traces/checkout-service
        select: count(*)
    formula: errors / total * 100
```

Check it, preview the changes, apply, and look at the data:

```sh
bronto dashboards validate -f checkout.yaml --live   # runs every query once, warns on an empty widget
bronto dashboards apply -f checkout.yaml --dry-run    # what would be created, changed or deleted
bronto dashboards apply -f checkout.yaml
bronto widgets query "p95 latency"
```

`bronto dashboards validate` without `--live` checks the file offline and reports each
problem with its file and line. With `--live`, it also resolves the datasets and runs each
widget's queries once, without saving anything. `-f` takes a file, a directory (every
`.yaml` and `.yml` file in it, one dashboard per file), or `-` for stdin.

`bronto dashboards export` goes the other way: it writes an existing dashboard as a
manifest that `apply` re-applies without changes, so a dashboard built in the web UI can
move into a file and into version control:

{/* test: tty */}
```console
$ bronto dashboards export "Checkout overview" > dashboard.yaml
$ cat dashboard.yaml
name: Checkout overview
description: Request rate, 5xx errors and latency for the checkout flow
tags:
  team: checkout
widgets:
  - name: Checkout requests
    type: line
    queries:
      - name: requests
        dataset: .traces/checkout-service
        select: count(*)
        where: $span.kind = 'SPAN_KIND_SERVER'
  - name: Checkout p95 latency
    type: line
    unit: nanoseconds
    queries:
      - name: p95_latency
        dataset: .traces/checkout-service
        select: p95($span.duration_nano)
        where: $span.kind = 'SPAN_KIND_SERVER'
        group_by:
          - $span.name
  - name: Checkout error rate
    type: line
    queries:
      - name: errors
        dataset: .traces/checkout-service
        select: count(*)
        where: $span.status_code = 'STATUS_CODE_ERROR'
      - name: total
        dataset: .traces/checkout-service
        select: count(*)
    formula: errors / total * 100
$ bronto dashboards validate -f dashboard.yaml 2>&1
✓ dashboard.yaml: dashboard "Checkout overview", 3 widgets
```

### How apply decides

- **The name is the identity.** `apply` updates the dashboard with the manifest's
  `name`, or creates one. If two dashboards have the name, it stops and lists both. It
  never deletes a dashboard.
- **Inline widgets belong to the dashboard.** `apply` tags each widget it creates with
  `managed-by: bronto-cli` and `bronto-cli-owner: <dashboard id>`, and finds it by name
  next time. Remove a widget from the file and the next `apply` deletes the widget and
  its metric definition.
- **A changed query gets a new definition.** Bronto can't update a metric definition, so
  `apply` creates a new one, points the widget at it, and then deletes the old one. If a
  run stops halfway, run it again: it picks up where it stopped.
- **`ref:` widgets are only attached.** `- ref: <widget name or id>` attaches an existing
  widget that something else manages. `apply` never changes or deletes it, and detaches it
  when you remove the `ref:`. A widget on the dashboard that the file doesn't mention, and
  that `apply` didn't create, is detached too.
- **Applying an export adopts.** Export a dashboard that `apply` didn't create and every
  widget becomes inline (a note on stderr says so). Applying that file tags them, and from
  then on `apply` manages them: leave one out and it's deleted. Group widgets and widgets
  with several definitions are exported as `ref:` entries.
- **A field you leave out is left alone.** Without `description`, `tags` or `layout`, or a
  widget's `type` or `description`, `apply` keeps the current value. With `tags:`, the file
  holds the dashboard's whole tag set. Bronto can't change a dashboard's description after
  creation, so `apply` warns instead.
- **An unchanged file makes no API writes.** `--dry-run` prints the plan and writes
  nothing; `-o json` prints it as JSON, with a `writes` count.

### Manifest fields

| Field | Meaning |
| --- | --- |
| `name` | The dashboard's name and identity. Required. |
| `description`, `tags` | Set on the dashboard. The description can only be set when the dashboard is created. |
| `widgets[].name` | The widget's name, unique in the file. |
| `widgets[].type` | `line` (the default), `bar`, `area`, `score`, `top-list`, `table`, `pie`, `donut`, `treemap`, `geomap`, `events-list`. |
| `widgets[].unit` | `nanoseconds`, `microseconds`, `milliseconds`, `seconds`, or a data size such as `bytes`, for every query and formula of the widget. `unit_config` takes the API's object instead. |
| `widgets[].queries` | Up to six queries; the widget's metric definition. |
| `widgets[].formula` | One formula over the queries by name, such as `errors / total * 100`. When a widget has a formula, the web UI plots only the formula. `formulas: [{name, expression}]` sets several, or names one. |
| `widgets[].ref` | An existing widget, by name or id, to attach. Takes no other field. |
| `queries[].name` | Default `q1`, `q2`, …; formulas refer to it, so no spaces. |
| `queries[].dataset` | A dataset as `-d` takes it (`name`, `collection/name` or id), or a list. Becomes the query's `from_expr`. `from_expr:` sets one directly, and `from:` takes dataset ids. |
| `queries[].select` | `count(*)`, a function such as `p95($span.duration_nano)`, or a field with `agg`. |
| `queries[].agg` | The aggregation: `count`, `sum`, `avg`, `min`, `max`, `p50`, `p75`, `p90`, `p95`, `p99`, `rate`, and more. Defaults from `select` (`count(*)` counts); a bare field needs it. |
| `queries[].where` | A filter in the [query language](https://docs.bronto.io/core-features/log-search/query-syntax). Default `""`, everything. |
| `queries[].group_by` | Up to five fields; one series per group. |
| `queries[].reduce_to` | How the series becomes one number: `avg` (the default), `sum`, `min`, `max`. |
| `layout` | Optional `[{widget, x, y, w, h}]` positions. Without it, the web UI lays the widgets out in two columns, ordered by widget id. |

The trace fields that dashboards use most: `$service.name`, `$span.name` (the operation),
`$span.kind = 'SPAN_KIND_SERVER'` (requests a service handled), `$span.duration_nano`
(nanoseconds, so set `unit: nanoseconds`), and
`$span.status_code = 'STATUS_CODE_ERROR'`.

## Dashboards and widgets

[Dashboards](https://docs.bronto.io/Search-and-Visualize/Dashboards) are built from
widgets. To build one from a file, use [`bronto dashboards apply`](#declarative-dashboards).
By hand, create the widgets first, then attach them to a dashboard. The API reference
covers [dashboards](https://docs.bronto.io/api-reference/dashboards/get-all-dashboards-for-an-organisation) and
[widgets](https://docs.bronto.io/api-reference/widgets/retrieve-all-the-widgets).

{/* test: tty */}
```console
$ bronto dashboards list

Checkout overview  Request rate, 5xx errors and latency for the checkout flow  2026-05-04  d4c6e2b5-7e91-42b4-af50-1b8e6d3c4f04
$ bronto dashboards get "Checkout overview"
{
  "description": "Request rate, 5xx errors and latency for the checkout flow",
  "id": "d4c6e2b5-7e91-42b4-af50-1b8e6d3c4f04",
  "metadata": {
    "created_at": 1777890000000,
    "created_by": "ada@example.com",
    "modified_at": 1781023500000,
    "modified_by": "ada@example.com"
  },
  "name": "Checkout overview",
  "tags": {
    "team": "checkout"
  },
  "widget_ids": [
    "3e5a7c9b-1d2f-4e6a-8b0c-2d4f6a8c0e11",
    "4f6b8d0c-2e3a-4f7b-9c1d-3e5a7b9d1f12",
    "5a7c9e1d-3f4b-4a8c-8d2e-4f6b8c0e2a13"
  ]

```

`widgets create` and `widgets update` both require `name` and `type`, and `update`
replaces the whole widget. Pass `metric_ids`, `widget_ids`, or `aux` as JSON values with
`-f`, or put the whole body in a file:

```sh
bronto widgets create --input widget.json
```

Then attach, remove, or detach. `bronto dashboards create` can't attach widgets in the
same call: the API ignores `widget_ids` there, so the CLI refuses a create body that
carries them and points you to `attach-widgets`.

```sh
bronto dashboards attach-widgets "Checkout overview" --widget-ids <widget>,<widget>
bronto dashboards remove-widget "Checkout overview" <widget>
bronto dashboards detach-from-template "Checkout overview"
```

- `bronto dashboards attach-widgets` adds widgets by id or unique name. `--widget-ids`
  takes a comma-separated list or can be repeated.
- `bronto dashboards remove-widget` takes the dashboard and one widget.
- `bronto dashboards detach-from-template` unlinks a dashboard created from a
  [template](#start-from-a-template) and confirms on stderr.

`attach-widgets` and `remove-widget` confirm on stderr, because the API answers them
with no body. With `-o json`, `-o jsonl` or `--jq` they print the updated dashboard
instead, so `--jq .widget_ids` shows what is attached now.

Only group widgets (type `group`) contain other widgets. `bronto widgets attach-widgets`
and `bronto widgets remove-widget` work the same way, with a group widget in place of the
dashboard:

```sh
bronto widgets attach-widgets <group-widget> --widget-ids <widget>
bronto widgets remove-widget <group-widget> <widget>
```

The dashboard, group widget, and widgets can each be an id or a unique name. All of these
commands support `--dry-run`.

`bronto dashboards update` changes either the `name` or the `layout`, one per call: the
API accepts exactly one of them. The CLI refuses a body with both, or with neither (a
`description` alone changes nothing), before sending it. Like the widget commands, it
prints the updated dashboard with `-o json`:

```sh
bronto dashboards update "Checkout overview" -f name="Checkout health" -o json
bronto dashboards update "Checkout health" --input layout.json
```

### Start from a template

Bronto ships ready-made dashboard templates, for example for AWS services, Nginx, or
OpenTelemetry host metrics. They are shared, read-only content. List them, then show one
to see what it would create: its parameters, its widgets, and the queries behind each
widget.

{/* test: tty */}
```console
$ bronto dashboards templates list

AWS Lambda                         3        b0d4f6c8-5e7a-4b9c-9d3e-4f5a6b7c8d91
$ bronto dashboards templates show "HTTP service overview"
HTTP service overview
id: e7a1c3f5-2b4d-4e6f-8a0b-1c2d3e4f5a61
Request volume and 5xx errors for an HTTP service

Parameters (pass with --param key=value):
  fromExpr  string  metric fromExpr

Widgets (2):

  Requests (line)
    query requests
      select:    count(*)
      where:     (none)
      from_expr: {{fromExpr}}

```

`bronto dashboards templates show` takes an id or a unique name. Bronto renders the
template without saving anything. A parameter you don't pass shows as a `{{name}}`
placeholder, here in each query's `from_expr`. Pass `--param key=value` to see the
queries with your value filled in. With `-o json` the command prints the whole rendered
template, with the template's `parameters` added.

To create the dashboard, pass the template and a value for each parameter:

{/* test: tty */}
```console
$ bronto dashboards create --template "HTTP service overview" --param fromExpr="\"collection\" = 'prod' AND \"dataset\" = 'checkout-service'" --dry-run
{
  "body": {
    "arguments": {
      "fromExpr": {
        "literal": "\"collection\" = 'prod' AND \"dataset\" = 'checkout-service'"
      }
    }
  },
  "dry_run": true,
  "method": "POST",
  "path": "/dashboards/templates/e7a1c3f5-2b4d-4e6f-8a0b-1c2d3e4f5a61/instance"
}
```

Drop `--dry-run` to create it.

Bronto copies the template's widgets and metric definitions into new objects and links the
dashboard to the template, which `bronto dashboards get` shows as `template.id`. A few
things to know:

- `--param` keys must be parameters the template declares, and each parameter needs a
  value. Otherwise the command lists the valid keys and exits with code 2. Some templates
  ignore a parameter and query fixed datasets; `show` tells you which.
- The dashboard takes the template's name. There's no name override, and a dashboard
  linked to a template can't be renamed. Run `bronto dashboards detach-from-template`
  first, then `bronto dashboards update <dashboard> -f name=<name>`.
- Deleting the dashboard leaves the copied widgets and metric definitions in place. To
  remove them too, note the widget ids from the `create` output first, then delete each
  with `bronto widgets delete`, and its definitions (the widget's `metric_ids`) with
  `bronto metrics definitions delete`.

`bronto widgets templates list` and `bronto widgets templates get <id>` show the
individual widget templates the dashboard templates are built from.

## Build a widget from a metric definition

A widget plots one or more metric definitions: saved queries, with optional formulas over
them, listed in the widget's `metric_ids`. These are not the ingested metrics that
`bronto metrics list` shows. `bronto metrics definitions` manages them, and
`bronto metrics definitions query` evaluates one, so you can check that a widget will show
data before you build it. The `/metrics/definitions` endpoint isn't in Bronto's published
API reference.

{/* test: tty */}
```console
$ bronto metrics definitions list
NAME                          DESCRIPTION              QUERIES  FORMULAS  CREATED     ID
checkout-service requests     Server spans per bucket  1        0         2026-06-09  6c1e9a2b-3d4f-4a5b-8c7d-9e0f1a2b3c51
checkout-service p95 latency                           1        0         2026-06-09  7d2fab3c-4e5a-4b6c-9d8e-0f1a2b3c4d52
Checkout error rate                                    2        1         2026-06-09  8e3b0c4d-5f6a-4c7d-8e9f-1a2b3c4d5e53
$ bronto metrics definitions query "checkout-service p95 latency"
SERIES       GROUP               STAT  VALUE    TREND
p95_latency  POST /api/checkout  p95   640 ms   ▂▂▂█▂▂▂▂
p95_latency  GET /api/cart       p95   95.0 ms  ▇▇▇█▇▇▇▇
```

`query` prints one row per series: each query and formula, or each group of a grouped
query, with its value over the range and a sparkline of the time buckets. The range is
`--since` (default `24h`), `--from`/`--to`, or `--time-range "Last 7 days"`, and `--slices`
sets the number of buckets. A time `unit_config` on the query makes the value read
`640 ms` instead of `640000000`. If every series is zero, a warning on stderr says so: the
query's `from_expr` or `where` most likely matches nothing. For data ingested in the last
few minutes, Bronto can keep answering a cached zero for a query it evaluated before the
data arrived. A new definition whose query differs, even only in its `where`, is
evaluated fresh. `-o json` prints the raw
[timeseries response](https://docs.bronto.io/api-reference/timeseries/retrieve-the-timeseries-for-a-metric-definition).

From definition to dashboard:

```sh
# 1. A definition: p95 latency of checkout-service's server spans, per operation
bronto metrics definitions create --input - <<'EOF'
{"name": "checkout-service p95 latency",
 "queries": [{"name": "p95_latency", "select": ["p95($span.duration_nano)"],
   "from_expr": "\"collection\" = '.traces' AND \"dataset\" = 'checkout-service'",
   "where": "$span.kind = 'SPAN_KIND_SERVER'", "groups": ["$span.name"],
   "aggregation": [{"time": "p95", "reduce_to": "avg"}],
   "unit_config": {"type": "time", "input": "nanoseconds", "output": "auto"}}]}
EOF

# 2. Check that it returns data
bronto metrics definitions query "checkout-service p95 latency" --since 24h

# 3. A line widget that plots it
def=$(bronto metrics definitions get "checkout-service p95 latency" -o json --jq .id -r)
bronto widgets create -f name="Checkout p95 latency" -f type=line -f "metric_ids=[\"$def\"]"

# 4. Attach it to a dashboard, and check every definition the widget plots
bronto dashboards attach-widgets "Checkout overview" --widget-ids "Checkout p95 latency"
bronto widgets query "Checkout p95 latency"
```

Each query needs a `name`, a `select`, a `where` (`""` for no filter), and `from_expr`,
such as `"collection" = '.traces' AND "dataset" = 'checkout-service'` for a trace dataset.
`from`, a list of dataset ids, also works, but `from_expr` doesn't depend on ids.
`bronto metrics definitions create` refuses a query without `where` or `from_expr`, which
the API would reject with a bare 400. A definition takes up to six queries. A formula such
as `{"name": "error_rate", "expression": "errors / total * 100"}` refers to queries by
name, and when a definition has one, the web UI plots only the formula.
`bronto metrics definitions create --help` has examples for a request count, a grouped
p95 latency, and an error-rate formula.

Definitions can't be updated, because the API has no update endpoint. Create a new
definition, set the widget's `metric_ids` to it with `bronto widgets update`, and delete
the old one with `bronto metrics definitions delete`. Deleting a widget doesn't delete its
definitions.

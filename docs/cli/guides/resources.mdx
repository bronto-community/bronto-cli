Every Bronto resource (datasets, monitors, API keys, and the rest) has a command, and
they all take the same verbs.

## The pattern

```sh
bronto <resource> list
bronto <resource> get <id-or-name>
bronto <resource> create -f key=value -f other=value
bronto <resource> update <id-or-name> -f key=value
bronto <resource> delete <id-or-name> --yes
```

For example:

## Names work wherever ids do

Every command that takes an id also takes a unique name:

- Datasets resolve by name, or by `collection/name` when the name exists in more than one
  collection.
- Users resolve by email.
- Roles resolve by id or `display_name`. System roles have readable ids such as `Admin`
  and `ReadOnly`.
- Monitors, dashboards, and the rest resolve by `name`. Quote names with spaces.

If a name matches more than one resource, the command fails with exit code 2 and lists the
matching ids.

## Creating and updating

`create` and `update` build the request body from repeated `-f key=value` flags. A value
that parses as JSON keeps its type (number, boolean, array, or object). Anything else is
sent as a string:

```sh
bronto dashboards create -f name=Overview -f description=Prod
bronto parsers update <id> -f name=nginx-combined
bronto groups create -f name=sre
```

For larger bodies, pass a JSON file with `--input`, or `--input -` to read stdin. `-f` and
`--input` can't be combined.

```sh
bronto monitors create --input monitor.json
./generate-monitor.sh | bronto monitors create --input -
```

The CLI sends the body unchanged, so use the fields the
[Bronto API](https://docs.bronto.io/api-reference/introduction) expects for that
resource. The example in each command's help (`bronto <resource> create --help`) lists
the fields the API requires.

Updates to `monitors`, `monitors templates`, `monitors downtimes`, `widgets`, `datasets`,
`forward-configs`, `webhooks`, `slack`, and `roles` use HTTP PUT, which replaces the whole
object. Send every field you want to keep, not only the one you change. A few other
updates need more than the changed field too:

- `groups update` needs both `name` and `description`. The API clears whichever one you
  leave out, so the CLI refuses an update without both.
- `datasets update` needs both `collection` and `dataset`, and `roles update` needs both
  `display_name` and `permissions`. The CLI refuses an update without them.
- `dashboards update` needs `name` (or a `layout`). A `description` is ignored.
- `saved-searches update` needs `name`, `log_ids`, and `search_details`.

## Deleting

`delete` asks for confirmation at a terminal. Without a terminal it can't ask, so it
fails with `usage_confirmation_required` (exit code 2) unless you pass `--yes`:

```sh
bronto api-keys delete <id> --yes
```

## Preview changes with --dry-run

`--dry-run` works on every command that changes something. It changes nothing, but reads
still run, so names resolve and an unknown name fails the same way it would without
`--dry-run`.

Every command that changes something prints the request it would send as a JSON plan on
stdout: method, path, and body. That includes `delete` and action verbs such as
`groups add-members`, `monitors mute`, and `users deactivate`. A name you pass shows up
as the id it resolved to in the plan's path. `delete` also skips its confirmation prompt,
because nothing is deleted.

{/* test: tty */}
```console
$ bronto dashboards create -f name=Overview -f description=Prod --dry-run
{
  "body": {
    "description": "Prod",
    "name": "Overview"
  },
  "dry_run": true,
  "method": "POST",
  "path": "/dashboards"
}
$ bronto monitors delete "Payments latency p95" --dry-run
{
  "dry_run": true,
  "method": "DELETE",
  "path": "/monitors/b2e4d0a3-5c7f-4092-8d3e-8f6c4b9a2d02"
}
```

## Commands beyond CRUD

A few resources have extra verbs:

| Command | What it does | Guide |
| --- | --- | --- |
| `bronto monitors events`, `bronto monitors notifications` | recent events and sent notifications | [Monitors](/cli/guides/monitors-and-dashboards#monitors) |
| `bronto monitors mute`, `bronto monitors check` | mute a monitor, lint definitions in CI | [Monitors](/cli/guides/monitors-and-dashboards#monitors) |
| `bronto dashboards attach-widgets`, `bronto dashboards remove-widget`, `bronto dashboards detach-from-template` | assemble dashboards | [Dashboards](/cli/guides/monitors-and-dashboards#dashboards-and-widgets) |
| `bronto widgets attach-widgets`, `bronto widgets remove-widget` | nest widgets | [Dashboards](/cli/guides/monitors-and-dashboards#dashboards-and-widgets) |
| `bronto groups members`, `bronto groups add-members`, `bronto groups remove-members` | group membership | [Access management](/cli/guides/access-management) |
| `bronto users groups`, `bronto users deactivate`, `bronto users reactivate`, `bronto users resend-invite` | user lifecycle | [Access management](/cli/guides/access-management) |
| `bronto datasets parser get`, `bronto datasets parser set`, `bronto datasets parser unset` | assign a parser to a dataset | below |
| `bronto metrics top-keys` | attribute keys seen on a metric | below |
| `bronto datasets monitors`, `bronto datasets dashboards` | what uses a dataset | below |
| `bronto forward-configs test` | check that Bronto can write to a forwarding destination | below |

### Assign a parser to a dataset

`bronto datasets parser` shows or changes which [parser](https://docs.bronto.io/core-features/custom-parser)
a dataset uses:

{/* test: tty */}
```console
$ bronto datasets parser get prod/checkout-service
{
  "parser_id": "8d0f2b4c-6e7a-4c9d-9f3b-4c6e8a0d2f16",
  "parser_name": "json"
}
```

```sh
bronto datasets parser set prod/checkout-service <parser>
bronto datasets parser unset prod/checkout-service
```

### Metric attribute keys

`bronto metrics top-keys <metric>` lists the attribute keys seen on a metric, the
metrics counterpart of `bronto fields`:

```sh
bronto metrics top-keys system.cpu.utilization --since 1h
```

### What uses a dataset

`bronto datasets monitors` and `bronto datasets dashboards` list the monitors and
dashboards that query a dataset. Check them before you delete or rename the dataset. They
print the same columns as `bronto monitors list` and `bronto dashboards list`:

{/* test: tty */}
```console
$ bronto datasets monitors prod/checkout-service
NAME                       WINDOW          THRESHOLD  CREATED     ID
High 5xx rate on checkout  Last 5 minutes  5          2026-05-04  a1f3c9d2-4b6e-4f81-9c2d-7e5b3a8f1c01
$ bronto datasets dashboards prod/checkout-service
NAME               DESCRIPTION                                                 CREATED     ID
Checkout overview  Request rate, 5xx errors and latency for the checkout flow  2026-05-04  d4c6e2b5-7e91-42b4-af50-1b8e6d3c4f04
```

### Test a forwarding destination

[Log forwarding](https://docs.bronto.io/core-features/log-forwarding) copies events to an
S3 bucket. `bronto forward-configs test` has Bronto write and delete a test object there,
so you can check the bucket policy before you create a forward config, or after you change
it. Name an existing forward config, or pass `--bucket` (with `--prefix` and
`--storage-class` if needed). Flags override the saved config's fields:

```sh
bronto forward-configs test --bucket my-archive-bucket --prefix bronto/
bronto forward-configs test <forward-config>
```

If Bronto can't write to the bucket, the command exits 1 with `forward_destination_failed`.

## API keys

`bronto api-keys create` is your one chance to copy a new key. Its output contains the
full key (`<id>.<secret>`), including the JSON it prints when piped, and the CLI reminds
you on stderr to store it. Bronto never returns the secret part again: `list` shows only
the key's id part.

`bronto api-keys list` masks that id part in every output format, JSON included, so it
doesn't leak into CI logs. Pass `--reveal` to see it in full.

{/* test: tty */}
```console
$ bronto api-keys list
NAME     API_KEY    CREATED     ID
docs-ci  bronto_d…  2026-05-04  7c9e1a3b-5d6f-4b8c-8e2a-3b5d7f9c1e15
```

## Usage

`bronto usage` shows ingestion, search, and export volume over a period (default `7d`):

{/* test: tty */}
```console
$ bronto usage --since 7d
TIME              EVENTS  VOLUME
2026-07-19 09:00  41      9.5 kB
2026-07-19 09:05  39      9.1 kB
2026-07-19 09:10  40      9.3 kB
2026-07-19 09:15  38      8.9 kB
2026-07-19 09:20  52      13.6 kB
2026-07-19 09:25  34      7.9 kB
```

For per-dataset numbers, call the API directly with
`bronto api GET /usage/organizations/logs` (see [the api command](/cli/extend/api)).
